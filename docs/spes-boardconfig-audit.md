# Redmi Note 11 Android BoardConfig audit (reference only)

## Source identity

Inspected the public Xiaomi Redmi Note 11 device tree:

- Repository: https://github.com/knyplaygrnd/android_device_xiaomi_spes
- Branch: `sixteen-qpr2`
- File: `BoardConfig.mk`
- Git blob: `98275ca85e583d1363b776f49dd24be01699564e`

This is an Android ROM build configuration, not a Mainline Linux DTS and
not a dump of the target handset's live boot chain.

## Values explicitly declared by this source

| Setting | Declared value | Interpretation |
|---|---|---|
| Device target | `spes,spesn` | Both codenames are accepted by this Android build |
| Platform | `bengal` | Qualcomm platform family identifier |
| Architecture | `arm64` | Android target architecture |
| Kernel image | `Image` | Android kernel image filename |
| Boot header | `3` | Android build is configured for boot image header v3 |
| DTB placement | `BOARD_INCLUDE_DTB_IN_BOOTIMG := true` | Android build config includes DTB in boot image |
| DTBO | `BOARD_KERNEL_SEPARATED_DTBO := true` | Android build expects a separate DTBO image |
| DTB build input | `khaje.dtb` | Android build points to a Khaje DTB |
| DTB directory | `device/xiaomi/spes-kernel/dtb` | Prebuilt DTB input directory |
| DTBO input | `device/xiaomi/spes-kernel/dtbo.img` | Prebuilt DTBO image input |
| Kernel cmdline console | `ttyMSM0` | Android config requests MSM serial console |
| Early console | `msm_geni_serial,0x4a90000` | Android config's early console setting |

## Important limits

These settings tell us how this particular Android ROM build is assembled.
They do **not** establish:

- the exact contents or DTB index of the stock phone's boot/vendor_boot;
- which DTBO overlay is selected by the bootloader on this handset;
- whether every spes/spesn hardware revision uses the same DTB;
- the actual RAM map, reserved-memory layout, or live FDT values;
- whether a Mainline Linux image can be booted using the same layout.

Do not copy the Android offsets, partition sizes, DTB selection, or boot-image
arguments into a Mainline boot image without inspecting the exact target
firmware and validating the bootloader hand-off.

## Consequence for this port

The board config strengthens the evidence that Android ROM builds for
spes/spesn use an Android boot header v3 setup with a separately built DTBO
and a Khaje-named DTB input. It is a useful comparison checklist for
read-only firmware inspection, but it does not supply a usable Mainline DTS.

Next source tasks:
1. Inspect the referenced `spes-kernel/dtb` and `dtbo.img` source project
   and record its exact revision and DTB inventory.
2. Compare the Android DTB's SoC and board nodes with supported Mainline
   bindings, preserving vendor-only nodes as reference data only.
3. Confirm the live DTB and active overlays from the exact handset before
   authoring a board DTS or image packaging.
4. Keep the no-flash release gate in `bringup-status.md` unchanged until
   physical-device boot and recovery are proven.

No kernel, DTS, boot image, or flashable artifact is generated by this audit.


## Follow-up: inspect the prebuilt DTB and vendor DTS source

Inspected the referenced prebuilt-kernel repository:

- Repository: https://github.com/knyplaygrnd/android_device_xiaomi_spes-kernel
- Branch: `sixteen-qpr2`
- Repository listing includes `dtb/`, `kernel-headers/`, `Image`, and `dtbo.img`.
- Fetched binary: `dtb/khaje.dtb`
- DTB blob SHA: `e88d620e961f9c505cc3bc3d29edacea4860b55a`
- DTB file size: 307,470 bytes; FDT header reports totalsize 302,427 bytes, version 17, last compatible version 16.
- The prebuilt `dtbo.img` is present in the repository listing, but its binary contents have not been decoded or audited here.

Inspected the corresponding downstream kernel source at commit
`4f39e412aa655767635da99903a6ffd42ca38872`:

- `arch/arm64/boot/dts/vendor/qcom/khaje.dts` declares
  `model = "Qualcomm Technologies, Inc. Khaje SoC"` and
  `compatible = "qcom,khaje"`.
- It includes `khaje.dtsi`.
- `khaje.dtsi` is a large Qualcomm vendor SoC description containing
  CPU/PSCI, interrupt, reserved-memory, peripheral, and power-management
  definitions.
- The inspected `khaje.dts` is a generic Khaje SoC DTS, not a
  board-specific Xiaomi Redmi Note 11 (`spes`) DTS.
- A source search did not locate a clear `xiaomi,spes` board compatible in
  this kernel repository. This is not proof that no board data exists in
  binary DTBs or overlays.

### Mainline implications

1. Treat `khaje.dtsi` as vendor reference material only. Its downstream
   bindings, reserved-memory declarations, regulator settings, and peripheral
   nodes cannot be copied wholesale into Mainline.
2. Do not assume `khaje.dtb` is the exact live DTB selected by every
   `spes/spesn` bootloader or firmware revision.
3. The prebuilt DTBO must be unpacked and its overlays identified before
   drawing conclusions about panel, touchscreen, sensors, or board revision.
4. We still need the target handset's read-only DTB/DTBO and firmware
   metadata to establish the actual board-specific nodes and overlay selection.
5. No device-specific Mainline DTS should be claimed complete based on this
   Android vendor source alone.


## Follow-up: map the downstream Khaje SoC include graph

Inspected `arch/arm64/boot/dts/vendor/qcom/khaje.dtsi` from
`knyplaygrnd/android_kernel_xiaomi_spes` at commit
`4f39e412aa655767635da99903a6ffd42ca38872`.

- Git blob: `29c39a2844583195f0e79ee2e4a2a3f8e2aeba04`
- File size: 103,679 text bytes.
- The file contains 29 include directives, including Khaje-specific clock,
  regulator, pinctrl, SDE/display, USB, and camera files, plus Bengal
  bus, GPU, audio, thermal, and PMIC definitions.
- It defines 155 labelled nodes in the parsed source, including eight CPU
  cores and a large `reserved-memory` section.
- The SoC DTSI's root memory node is a placeholder with a zero-sized
  `reg`; it is not a usable physical RAM map for the handset.
- It includes vendor Android firmware / memory-sharing and Qualcomm-specific
  services. Those definitions must be checked against Mainline bindings and
  actual firmware behavior individually.
- A repository code search for `model = "Redmi Note 11"`,
  `xiaomi,spes`, and `spes.dts` did not find a board DTS in this source
  index. This is limited search evidence, not proof that no board data exists.

### DTBO binary inspection limitation

The GitHub file endpoint returned the `dtbo.img` blob SHA
`064617492f5a4f84c13de52aa6f8557f786064a0`, but did not return decodable
binary bytes through the text-file interface. Fetching the blob as UTF-8
failed on non-UTF-8 bytes. Therefore no DT table header, overlay count,
board IDs, or overlay contents are claimed as inspected. The file must be
downloaded as a binary artifact or extracted from the handset before analysis.

### Porting consequence

Do not copy the vendor reserved-memory map into a Mainline DTS. Its fixed
addresses and carveouts depend on the exact firmware and RAM variant. First
obtain the target phone's live FDT and boot firmware metadata; then identify
the minimum required carveouts and translate only supported hardware nodes.


## Read-only DTBO inspection helper

Added `scripts/inspect_android_dt_table.py` to parse the Android DT table
header and entry metadata, validate embedded FDT headers, and emit JSON.
It is deliberately read-only and does not modify or flash an image.

When a genuine binary `dtbo.img` is available locally, run:

```sh
python3 scripts/inspect_android_dt_table.py /path/to/dtbo.img
```

The report includes each entry's index, byte offset and size, board ID,
revision, custom fields, and FDT header metadata. These numeric fields are
not sufficient by themselves to identify the active overlay; correlate them
with the exact firmware, bootloader selection rules, and device variant.
